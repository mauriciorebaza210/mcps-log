Route drive-time optimization

Included for completeness, with an honest caveat: most of this is already running in production today.

Read this first. When I went looking for what to build here, I found the optimizer already shipped. getRouteData() in appscript/RouteData.js builds a driving-distance context and nearest-neighbor orders every operator's day before the schedule ever reaches the browser. What follows separates what exists from what would actually be new — because the new part is thin.
Screen 1What ships today

This is not a proposal. This is the code path that runs every time anyone opens the schedule.

appscript/RouteData.js — line 196
196 const distCtx = buildDistanceContext_(); // cached driving minutes 197 198 const pools = orderDayPoolsByOperator_(dayPools[dayName], distCtx); 199 ↑ groups by operator, nearest-neighbor orders each group

Which means the following already works

orderStopsNearestNeighbor_ in appscript/RouteOrdering.js walks each technician's day picking the closest unvisited stop, using real driving minutes from drivingMinutes_, backed by the Geocode_Cache sheet so it isn't re-geocoding on every load. Stops are already sequenced sensibly before the technician ever sees them.

The honest gap is not the ordering. It is that nobody can see the number — there is no drive time anywhere in the interface, so there is no way to tell a good route day from a bad one, and no way to notice when a new pool has made someone's Tuesday twenty minutes worse.

Screen 2Make the drive time visible

The cheapest genuine improvement here. The numbers already exist in distCtx — they are computed and then thrown away. Surfacing them costs almost nothing and turns route quality into something you can actually manage.

Why this is worth having

Right now a day that quietly grew from 50 minutes of driving to 95 looks identical in the interface. With the number visible you can see it happen, and you can see which new pool caused it — which is the input to deciding whether a customer on the far side of town is worth taking on at the quoted price.

Screen 32-opt refinement, offered rather than applied

Nearest-neighbor is fast but it makes a classic mistake: it takes the closest next stop and paints itself into a corner, then has to drive back across everything. A 2-opt pass looks for pairs of stops that could be swapped to shorten the total. Typical gain over nearest-neighbor is 5–12%.

Offered, never forced

This is the part that decides whether the feature succeeds. Technicians build a rhythm — which house has the dog, which gate sticks, which customer is always home at ten. Silently reshuffling their day loses trust fast, and they will route around the software rather than with it. So the optimizer proposes, shows its arithmetic, and waits.

Screen 4Pinned stops — the human constraints

The reason pure distance optimization disappoints in real service businesses: distance is not the only constraint, and the others are not in the data. Pins let a human write them down once so the optimizer has to respect them.

What a pin is

A stop locked to a position — first, last, or before/after a given time — with a one-line reason attached. The optimizer orders everything around the pins instead of ignoring the constraint and being overruled by hand every week. The reason is visible to whoever covers the route when the regular technician is out, which is when this knowledge normally gets lost.

The arithmetic

Twenty minutes a week is real, and it compounds. But it is a smaller number than it looks, because the expensive part of the ordering problem was already solved. The optimizer is not being added — it is being tuned.

Meanwhile sketch 1 addresses green pools, which cost a re-clean, a chemical burn, an apology and sometimes the customer. Sketch 2 addresses photos being deleted right now, today, on visits already completed. Both are larger numbers than twenty minutes of driving.

Recommendation: don't build this yet — with one exception. The drive-time readout from Screen 2 is worth pulling out on its own. The numbers are already computed and discarded; surfacing them is a couple of hours, and it gives you a way to see route quality degrading and to price distant pools correctly. That's the piece with genuine leverage. The 2-opt pass and pinning can wait until the routes are big enough that 6% is a number worth chasing.
